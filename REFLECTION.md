# Project Reflection

## 1. Hardest bug and debugging process
The most challenging technical hurdle I encountered was an intermittent server 500 error on the deployed Vercel instance when requesting the AI-generated personalized audit summary. During local testing, the Express API functioned flawlessly, which initially suggested a environment variable config issue. My first hypothesis was that the OpenRouter API credentials were not loading correctly in production, so I added logging to verify key injection. However, the keys were present. The second hypothesis was a timeout limit. Vercel serverless functions on the hobby plan enforce a strict ten-second limit. By measuring the response duration of the OpenRouter owl-alpha API locally, I discovered it averaged twelve to fourteen seconds to return the complete audit text.

To debug and resolve this, I refactored the backend server to stream the response data using a Chunked Transfer Encoding stream. By establishing a stream connection from the Express backend and forwarding OpenRouter chunks directly to the frontend, the response was registered as active by Vercel before the ten-second threshold, preventing the gateway from terminating the request. On the client side, I implemented a reader utilizing TextDecoder to parse the stream and update the dashboard state in real time. This not only prevented API crashes but also greatly enhanced the user experience by reducing perceived loading times.

## 2. A decision reversed mid-week
At the start of the week, I decided to build the application on Next.js using the App Router. My rationale was that server-side rendering would be required to generate dynamic Open Graph meta tags for the shared report pages, ensuring that shared URLs would look polished when posted on Twitter or Slack. However, as the project scope progressed into Day 2, I realized that Next.js introduced unnecessary complexity and overhead for what was fundamentally a client-driven utility. Combining the deterministic audit calculations in auditEngine.ts with Server Actions blurred the architectural boundaries and slowed down local iteration speeds.

I chose to reverse this decision, migrating the stack to a decoupled Vite React single-page application supported by a lightweight Express server. This structure allowed for extremely fast development cycles and kept the core frontend lightweight. For the Open Graph tag problem, I realized we could use a static head configuration and fallback logic. The Express server was dedicated purely to handling secure API routing, OpenRouter summary calls, and database persistence. This decoupling ensured clean code architecture, eliminated unnecessary cold start latencies, and made debugging individual elements of the application significantly more straightforward.

## 3. What I would build in week 2
If I had a second week to develop this product, I would focus on integrating a secure, direct expense scanner. Currently, the application relies on manual user inputs, which are subject to estimation errors or forgotten subscription seats. I would implement an API connection using Plaid or a similar financial data aggregator to let startup founders securely connect their business credit cards. The application would parse statement histories, automatically identify SaaS line items from vendors like OpenAI, Anthropic, Cursor, and GitHub, and generate the audit instantly.

Additionally, I would develop an automated invoice parser using a PDF parsing library. Users could upload their billing PDFs, and the system would parse seats and tiers automatically. I would also build out a collaborative dashboard showing team-wide spend optimization metrics, allowing engineering managers to see which licenses are unused. Finally, I would introduce a benchmark visualization system comparing developer spend against similar-sized teams in the same industry, adding high-value comparative insights to the audit page.

## 4. How I used AI tools
I used Claude 3.5 Sonnet through Cursor to assist with structural design, code scaffolding, and draft reviews. AI was highly effective at generating standard Tailwind CSS component configurations, styling the dark-mode dashboard cards, and writing the initial unit test suites in Vitest. I did not trust the LLM with the core audit math and financial calculations. Initially, I attempted to feed the raw user input directly to the model and asked it to calculate potential savings. The model consistently hallucinated mathematical calculations, fabricated plan pricing tiers, and provided inconsistent recommendations.

To solve this, I designed the audit engine to run on deterministic, hardcoded rules in typescript (auditEngine.ts) to guarantee absolute mathematical accuracy. I constrained the AI's role strictly to generating the narrative executive summary, passing it the pre-calculated savings data in the prompt. This separation of concerns ensured that the core application math remains perfect, while the AI contributes a polished, conversational report.
